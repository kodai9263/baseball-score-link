# スコア連携アプリ UI/UXデザイン引き継ぎ書

作成日: 2026-09-09  
対象: Claude CodeによるUI/UX改善  
優先度: モバイルの試合中入力 > 状況把握 > ライブ共有 > 紙スコア確認

## 1. 依頼の目的

現在のMVPを、少年野球の試合中でも迷わず使える、モダンで実用的な画面に改善してください。

単に装飾を増やすのではなく、屋外でスマートフォンを片手操作する保護者・スコアラーが、現在の試合状況を一目で確認し、少ない判断とタップで打席結果を記録できることを最優先にします。

目指す印象は以下です。

- 清潔感があり、信頼できる
- スポーツらしい活気はあるが、子どもっぽくない
- 情報量が多くても現在地と次の操作が明確
- 初心者にも分かりやすく、経験者にも遅く感じさせない
- 紙のスコア文化を尊重しつつ、操作はデジタルに最適化されている

## 2. プロダクト概要

少年野球チーム向けのスコア入力・ライブ共有・紙スコア清書アプリです。

中心となる利用者は次の4者です。

1. 試合中にスマホで入力する保護者スコアラー
2. ベンチや離れた場所から試合状況を見る監督・コーチ
3. ライブスコアを見るチーム関係者・保護者
4. 試合後に記録を確認・補正する経験者

この段階では1画面のローカルMVPです。現状の詳しい企画は `docs/baseball-score-app-spec.md` を参照してください。

## 3. 現在の実装

### 技術構成

- Next.js App Router
- React 19
- TypeScript
- Tailwind CSS
- Lucide React
- Supabase（設定がなくてもローカル試作として動作）

### 主なファイル

- `src/app/page.tsx`: 画面、ローカル状態、打席記録・取消ロジック
- `src/app/globals.css`: 全体背景、フォーカス、reduced motion
- `src/app/layout.tsx`: メタデータとviewport
- `tailwind.config.ts`: 色・フォントトークン
- `src/lib/score-data.ts`: 選手、打順、打席結果、初期状態
- `src/lib/types.ts`: ゲーム状態とイベント型

### 現在の画面要素

- ヘッダー
  - アプリ名
  - Supabase接続状態
  - 記録の暫定・確定状態
- 試合状況
  - 回、表裏、アウト、現在打順
  - 両チームの得点
  - 一・二・三塁の走者
- 打席入力
  - 現在の打者
  - 11種類の打席結果
  - 確定
  - 直前プレーの取消
- ライブ共有
  - 6回までのイニング別得点表
- 紙スコア風プレビュー
  - 9人分の打順と6回分の記録セル
- 直近プレー
  - 最大6件の履歴

今回はUI/UX改善が中心です。既存機能とデータ構造は維持してください。

### 必ず維持するもの

- 打席結果の選択と確定
- 走者・得点・アウト・回の更新
- 3アウト時の表裏切り替え
- 直前プレーの取消と状態再構築
- イニング別得点

- 直近プレー

## 5. 推奨するデザイン方針

### コンセプト

**Modern Field Utility** — 野球場の落ち着いた緑と、記録ツールとしての明快さを組み合わせた、モバイルファーストの実用UI。

フラットで整理された面構成を基本にし、重要な状態だけをカード、背景色、太い数字で強調します。強いグラデーション、過剰なガラス表現、装飾目的のアニメーションは避けてください。

### カラー

既存のフィールドグリーンをブランドの軸として活用します。

| 用途 | 推奨色 | 意図 |
| --- | --- | --- |
| Primary | `#247044` | 野球場、安心感、主要な選択状態 |
| Primary dark | `#173F2A` | 得点面、強い見出し、濃色面 |
| Primary soft | `#E7F4EA` | 選択状態、走者あり、補助背景 |
| Action | `#EA580C` 前後 | 確定など画面内の唯一の主要CTA |
| Background | `#F8FAFC` | 全体背景 |
| Surface | `#FFFFFF` | カード、入力面 |
| Text | `#172033` 前後 | 主本文 |
| Muted text | `#596579` 前後 | 補足。ただしコントラストを確保 |
| Border | `#D7DDE5` | 控えめな区切り |
| Error | `#B91C1C` | エラー、危険操作 |

色だけで状態を伝えず、必ず文字・アイコン・形のいずれかを併用してください。通常文字は背景とのコントラスト比4.5:1以上を目標にします。

### タイポグラフィ

- 日本語を主役にし、本文はシステムUIフォントを優先
- 英数字・得点・回数はtabular numbersを使用
- 本文はモバイル16pxを基本にする
- 情報階層は色を増やすより、サイズ・太さ・余白で作る
- 推奨スケール: 12 / 14 / 16 / 18 / 24 / 32px
- 行間: 本文1.5前後

外部Webフォントは新たに導入しなくて構いません。試合会場の不安定な通信でも表示が安定することを優先します。

### 形・余白・アイコン

- 4px / 8px単位の余白体系
- カード角丸: 12〜16px
- ボタン角丸: 10〜12px
- 影は弱く1〜2段階。枠線との併用を増やしすぎない
- アイコンは既存のLucideで統一
- 絵文字をナビゲーションや状態アイコンとして使わない
- タップ領域は最低44×44px、主要操作は48px以上

## 6. 推奨する情報設計

### モバイル（最優先）

画面上部から次の順序を推奨します。

1. コンパクトな試合ヘッダー
   - 対戦カード、回の表裏、暫定状態
   - 接続状態は主要情報と競合しない小さな表示
2. 常時把握したいスコアボード
   - 両チーム得点を最大級の数字で表示
   - アウトと走者状況を同じ視野に置く
3. 現在の打者
   - 打順、選手名、背番号、守備位置
4. 打席結果入力
   - 結果を意味ごとに整理して選びやすくする
5. 画面下部の主要操作
   - `この内容で記録` を主CTAにする
   - `直前を取り消す` は明確に副操作へ下げる
6. ライブスコア、直近プレー、紙スコア
   - 試合中入力の邪魔をしない下位セクション

紙スコア表は横幅が必要なため、モバイルで無理に縮小しないでください。横スクロールであることを視覚的に示すか、折りたたみ・詳細表示にしてください。

### デスクトップ

- 最大幅は1200〜1280px程度
- 左または中央に試合状況と入力を配置
- 右側にライブスコアと直近プレーを配置
- 紙スコアは横幅を活かして下段全幅でもよい
- 重要な入力領域はスクロール中も追いやすくしてよいが、固定要素がコンテンツを隠さないこと

## 7. コンポーネント別の要件

### 試合ヘッダー

- 現在の `スコア連携アプリ MVP` は、利用中の画面名としてより自然な名称へ整理してよい
- 開発状態の `ローカル試作` は、スコアや記録状態より目立たせない
- `暫定` は記録の状態だと分かるラベルにする
- ヘッダーを大きくしすぎず、モバイルのファーストビューを入力に使う

### スコアボード

- 3秒以内に「何回の表裏か、何対何か、何アウトか」が分かる
- 得点は最も視認性の高い数字にする
- 攻撃中チームが分かる印を追加してよい
- アウト表示は数字に加え、3つのドットなどの冗長表現も可
- 走者状況は野球のダイヤモンド形が直感的。難しければ現行の3カードでもよい
- 走者名が長くても崩れない

### 打席結果入力

11個のボタンを平坦に並べるだけでなく、認知負荷を下げるグルーピングを検討してください。

- 安打: 単打、二塁打、三塁打、本塁打
- 出塁: 四球、死球、失策出塁
- アウト: 三振、ゴロアウト、フライアウト、犠打

ただしタブを切り替えないと目的の結果に到達できない構成は避けます。頻出操作が1タップ余計になるためです。見出し、色の薄い面、ボタン形状の差などで同一画面内に整理してください。

選択中の結果は、色だけでなくチェックアイコンや枠でも明確にします。記号（`1B`, `BB`, `5-3`など）は初心者向け名称より目立たせすぎないでください。

### 確定・取消

- 1画面の主CTAは確定操作のみ
- ラベルは `確定` より `この内容で記録` の方が目的が明確
- 選択した結果をCTA付近に再掲し、誤入力を減らす
- 記録中は二重送信できない見た目と状態を想定
- 取消は副ボタンとし、イベントがないときは見た目・属性ともにdisabled
- 取消後に何を戻したか分かる短いフィードバックを将来追加しやすい設計にする

### ライブ共有

- 表の情報を保ったまま、モバイルで合計得点が見切れない工夫をする
- チーム名と合計列は強調する
- 現在のイニングを示す状態があると望ましい
- 数字列はtabular numbersを使う

### 直近プレー

- 最新の1件を最も目立たせる
- 回表裏、選手名、結果、打点、追加アウトの順に読みやすく整理
- 長いリストは将来折りたたみ・全件表示へ発展できる形にする
- 空状態では「まだありません」だけでなく、最初の打席結果を選ぶ案内を短く表示

### 紙スコア風プレビュー

- これは入力UIではなく出力プレビューであると明示
- 表の罫線と記号の可読性を優先し、装飾を控える
- 横スクロール領域には視覚的なヒントを付ける
- スクリーンリーダー向けに、将来的な表形式の代替情報を意識する

## 8. インタラクション

- クリック・タップ後100ms以内に視覚的フィードバックを返す
- hoverだけに意味を持たせない
- hover / pressed / selected / disabled / focus-visibleを定義する
- マイクロインタラクションは150〜250msを基本にする
- transformやopacity中心とし、レイアウトが動く演出は避ける
- `prefers-reduced-motion` では不要な動きを無効化する
- ボタン選択時に周辺レイアウトをずらさない
- モバイルで固定CTAを採用する場合、safe areaと本文下部の余白を確保する

## 9. アクセシビリティ

- HTMLの見出し順を維持する
- icon-onlyボタンには名前を付ける
- 選択ボタンには `aria-pressed` を使う
- 現在の状態や更新結果は、将来的に `aria-live` で通知できる構造にする
- フォーカスリングを消さない
- キーボードだけで全操作を完了できる
- タップ領域は最低44×44px
- 本文・ボタンのコントラスト比4.5:1以上
- 情報を色だけで伝えない
- 200%拡大でも主要操作が欠けない

## 10. 実装時の進め方

1. まず既存コードとこの文書を読み、変更方針を短く提示する
2. `src/app/page.tsx` の状態更新ロジックをUIから分離する必要がある場合も、挙動を変えない小さな変更に留める
3. 最初にモバイル375pxの入力体験を整える
4. 次に768px、1024px、1440pxへ拡張する
5. 必要に応じて表示コンポーネントを同ファイル内または小さなcomponents群へ分ける
6. `tailwind.config.ts` とCSS変数に意味ベースのトークンを集約する
7. lint、typecheck、buildを実行する
8. 実画面で操作し、記録→表示更新→取消→元の状態への復元を確認する

大規模なコンポーネントライブラリの導入は不要です。既存のTailwind CSSとLucide Reactで十分です。新しい依存関係が本当に必要な場合は、インストール前にユーザーの許可を取ってください。

## 11. 完了条件

### 機能

- 11種類すべての打席結果を選択・記録できる
- 選択状態が明確に見える
- 記録後に打者、走者、得点、アウト、回表裏、履歴が正しく更新される
- 3アウトで走者がクリアされ、表裏が切り替わる
- 取消で直前の状態へ正しく戻る
- イニング別得点と紙スコアが既存どおり表示される

### レスポンシブ

- 375pxで横方向にページ全体がはみ出さない
- 紙スコアなど意図した横スクロール領域だけが横に動く
- 768px、1024px、1440pxで情報密度と余白が不自然でない
- 固定要素がボタン・表・履歴を隠さない

### 品質

- `npm run lint` が通る
- `npm run typecheck` が通る
- `npm run build` が通る
- フォーカス、hover、pressed、selected、disabledが確認できる
- reduced motionでも操作に支障がない
- 主要な文字・ボタンのコントラストが十分

### 実画面レビュー

最低限、以下のスクリーンショットを提示してください。

1. モバイル375px: 初期状態
2. モバイル375px: 打席結果選択後
3. モバイル375px: 複数プレー記録後
4. デスクトップ1440px: 全体

スクリーンショットだけでなく、実際に記録と取消を操作した結果も報告してください。ビルド成功だけを画面確認の代わりにしないでください。

## 12. 避けること

- 既存の試合進行ロジックをUI改善と同時に全面改修する
- 重要度に関係なくすべてを同じカード・同じ強さで並べる
- モバイルで紙スコア全体を極端に縮小する
- 低コントラストな薄いグレー文字を多用する
- 緑、青、オレンジなど強い色を同じ優先度で乱用する
- 主CTAを複数作る
- 絵文字を操作アイコンとして使う
- hoverしないと意味が分からない操作
- タップ時にカードや周辺レイアウトが動く演出
- 見栄えのためだけの重いアニメーションや背景装飾
- スマホ画面の確認なしで完了とする
