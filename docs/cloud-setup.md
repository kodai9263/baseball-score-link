# チーム共有・本番接続手順

確認日：2026-09-12。機能は実装済みですが、本番のSupabase・メール送信・公開URLへの接続は未実施です。

## 利用の流れ

1. メールの確認コードでログインする。初回はアカウントも作成される。
2. チーム名と自分の表示名でチームを作成する。作成者が管理者になる。
3. 9人と最初の試合を登録する。空のクラウドには、同じURLの端末内記録をコピーすることもできる。コピー元は残す。
4. 管理者が招待先メールと権限を指定し、発行したコードを本人へ渡す。アプリから招待メールは送らない。
5. 招待先本人が同じメールでログインしてコードを入力する。有効期限7日・1回限り。取り消しもできる。

| 権限 | 記録・メンバー・試合の編集 | 閲覧・成績・JSON書き出し | 招待・権限管理 |
| --- | --- | --- | --- |
| 管理者 | 可 | 可 | 可 |
| 記録者 | 可 | 可 | 不可 |
| 閲覧者 | 不可 | 可 | 不可 |

最後の管理者を降格・解除することはできない。先に別の参加者を管理者へ変更する。未参加者・未ログイン利用者はクラウド記録を取得できない。

## 本番で必要な設定

### 1. Supabase DB

本番用プロジェクトを確定してから、SQL Editorまたは管理されたマイグレーション手順で `supabase/migrations/202609120001_team_cloud.sql` を一度適用する。既存の試合テーブルの変更やデータ削除はない。新規の `score_*` 4テーブルとRPC・RLSを作る。

`supabase/tests/bootstrap.sql` は使い捨ての検証DB専用。本番では絶対に実行しない。実際のSupabaseが管理する `auth.users` やロールを作り直さない。

### 2. メール認証

Email認証・新規登録を有効にし、確認メールの送信を有効にする。Magic Linkのメールテンプレートをコード形式に変更する。新規登録の確認テンプレートも同じコード案内に揃える。

```html
<h2>スコア連携アプリの確認コード</h2>
<p>アプリの確認コード欄に入力してください。</p>
<p>{{ .Token }}</p>
<p>このメールに心当たりがなければ、操作する必要はありません。</p>
```

確認コード方式のためアプリ側の認証コールバックページは不要。Site URLは本番HTTPS URLに設定する。一般利用者に送るため、独自SMTPと送信元を設定して配信を確認する。標準SMTPはテスト用途の制限があり、本番のメール配信として扱わない。[Supabase OTP手順](https://supabase.com/docs/guides/auth/auth-email-passwordless)、[SMTP手順](https://supabase.com/docs/guides/auth/auth-smtp)を参照。

### 3. アプリの環境変数とホスティング

`.env.example` の2項目を公開先の環境変数管理画面に設定する。ローカル検証はGit対象外の `.env.local` を使う。

- `NEXT_PUBLIC_SUPABASE_URL`：本番プロジェクトURL
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`：ブラウザ用の公開キー（anonまたはpublishable key）。service_roleやsecret keyを入れない。

これらはビルド時に組み込まれるため、変更後は再ビルド・デプロイが必要。両方未設定なら端末保存モードで起動する。

公開先はNext.js対応・Node.js 22を使用する。依存復元は `npm ci --legacy-peer-deps`、ビルドは `npm run build`、Nodeサーバーで配信する場合は `npm start`。HTTPSで運用する。

## 保存と復旧

- 1チームのスコアブック全体をJSONとして保存する。上限10MB。複数試合・交代・DH・選手の学年情報を含む。
- 保存成功の応答が届いてから画面に反映する。通信失敗時は保存結果が不明な場合もあるので、再読み込みで確認する。
- 更新番号を比較し、古い画面からの上書きを拒否する。通信に失敗した操作の自動再送やオフライン同期は行わない。
- 閲覧者は15秒ごとと画面復帰時に最新を取得する。記録者は他の人の更新を検知すると入力を止め、再読み込みを案内する。即時配信方式ではない。
- 権限一覧は20秒ごとに更新する。変更直後に古い画面が残っていても、DB側の保存権限は毎回検証する。
- JSONバックアップは従来どおり可能。定期的に保管し、Supabase側のバックアップ方針も決める。
- 開発URLと公開URLの端末データは別領域。開発URLでJSONを書き出し、公開URLの端末保存モードで最初の登録後に復元し、ログインして空のチームへコピーできる。既にクラウドの記録がある場合はバックアップ画面で内容を確認して復元する。
- 障害時はアプリを直前の版へ戻す。DBテーブルを削除して戻さない。書き出したバックアップを保管し、必要な復元は対象チームと内容を確認して実施する。

## 検証

自動テストに加え、空のPostgreSQLに認証の最小スタブと本番マイグレーションを適用して、RLS・役割・招待の本人照合/期限/再利用/取消・最後の管理者・競合保存を検証する。

```bash
# 自分で用意した空の使い捨てDB。DB名は score_cloud_test に限定する。
export DATABASE_TEST_URL='postgresql://postgres:TEST_PASSWORD@localhost:5432/score_cloud_test'
bash scripts/test-cloud-db.sh
```

既に適用した検証DBでは `psql "$DATABASE_TEST_URL" -X -v ON_ERROR_STOP=1 -f supabase/tests/team_cloud.sql` でテストだけ再実行する。テストのデータはトランザクションでロールバックする。

画面検証補助の `scripts/cloud-preview-server.mjs` はlocalhostの使い捨てDBだけに接続し、認証部分を仮のコードに置き換える。本番アプリには含めない。実メールやSupabase Authそのものを検証したことにはならない。

## 接続後に必ず確認すること

- 本番の実メールで新規登録・再ログイン・ログアウトができる。
- 管理者、記録者、閲覧者、別チームのアカウントで実際のSupabase APIの権限が一致する。
- PCとスマートフォンで入力→保存→再読み込み→成績を確認する。
- 別端末に同じ試合が表示され、競合時に上書きされない。
- JSON書き出し・復元と既存ローカルデータの移行ができる。
