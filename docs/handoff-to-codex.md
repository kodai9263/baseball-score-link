## 3. 覆す前に読んでほしい設計判断

いずれも理由があって選んでいる。変えるなら理由ごと見直すこと。

### 3.1 Action色を `#c2410c` にした

引き継ぎ書は `#ea580c` を指定しているが、白文字とのコントラストが3.54:1で、同じ引き継ぎ書§9の「4.5:1以上」を満たさない。`#c2410c` なら5.18:1。**指定色に戻すとアクセシビリティ要件を割る。**

### 3.2 犠打は全走者を1つ進め、3アウト目では得点を認めない

修正前は打者がアウトになるだけで走者が動かず、犠打として成立していなかった。三塁走者は生還させる（スクイズを記録できるようにするため。ユーザーの選択）。

ただし3アウト目になる犠打では得点も進塁も認めない。打者走者が一塁に触れる前に第3アウトが成立するため（公認野球規則5.08(a)）。**この分岐を外すと「3アウトなのに点が入る」不具合になる。**

### 3.3 紙スコアは早稲田式の記入法

ネットで実際の書き方を調べて合わせた。

- ひし形の頂点は下から反時計回りに 本塁・一塁・二塁・三塁
- 到達した塁まで塁間に斜線を引く
- 打席結果の記号は一塁の区画（右下）
- 中央はアウトなら `I`/`II`/`III`、生還なら `●`、残塁なら `ℓ`（3つは同時に起こらないので共用）
- アウトのプレーの記号には下線、3アウトチェンジは右下角に斜線2本
- 左下の点は打点（これは簡略表現。本来は進塁させた打者の打順を丸で囲む）

**マスの向きは出典によって3通りに割れていた**（Wikipedia・検索要約は右下=一塁、少年野球メモは左下=一塁、パ・リーグ.comはさらに別）。「打席結果を一塁側=右下に書く」点は複数出典で一致していたので、それを満たし、かつ守備位置から見た実際のダイヤモンドと同じ向きになる配置を採用した。実物のスコアブックと突き合わせる価値はある。

### 3.4 得点したマスに薄い緑を敷いている

紙にはない表現。得点を数えやすくするために足した。中央の `●` と塁間の太線があるので色だけの表現にはなっていない。紙の再現性を優先するなら外してよい。

### 3.5 vitestは4系、インストールに `--legacy-peer-deps` が必要

- 5系は `@types/node ^22` 以上を要求し、本プロジェクトの `^20.14.10` と衝突する（Node実体は22.17.0なので `@types/node` を22系に上げるのが本筋だが、依頼の範囲外なので触っていない）
- npm 10.9.2 は vitest の optional peer 解決でクラッシュする（`Cannot read properties of null (reading 'edgesOut')`）。`package.json` に直接書いて `npm install --legacy-peer-deps` で入れた
- 既存パッケージのバージョン変更は0件であることを `package-lock.json` の差分で確認済み

## 4. 未着手の課題

### 4.1 ゴロアウトでの進塁打（要方針決定）

内野ゴロで走者が進むケースに未対応。併殺・封殺・野選・進塁打で結果が変わるのに、`ゴロアウト` という1つの選択肢では判断材料が足りない。推測で実装すると記録を壊す。

仕様書§9の入力モード設計（打球方向・守備処理の入力、§10.1の走者進塁の確認ステップ）と一緒に決めるべき。**単独で実装しないこと。**

### 4.2 紙スコアが表と裏の記録を同じ行に混ぜている

元のMVPが両チームで1つの打順データ（`lineup`）を共有しているため、紙スコアの9行に表と裏の記録が混在する。本来はチームごとに表を分ける必要がある。データモデルの変更を伴うので今回は触っていない。**実戦投入前には必須。**

### 4.3 依存の脆弱性（要判断）

`npm audit` で3件。いずれも今回の追加分ではなく元からのもの。

| パッケージ | 深刻度 | 内容 |
|---|---|---|
| `next` | critical | Windowsホストでの未認証RCE、画像最適化APIのRCE |
| `sharp` | high | libheif の脆弱性 |
| `nanoid` | high | サイズ0で無限ループ |

`npm audit fix` で解消できるが `next` のバージョンが上がる。公開前には必須。

### 4.4 その他の既存の簡略化

- 3アウト目の得点抑止は犠打の分岐にのみ入れている。他の結果で得点が発生するようになったら一般化が必要
- 打点は左下の点。本来は進塁させた打者の打順を丸で囲む記法（マスの幅が足りず見送り）
- 公式記録判定層（仕様書§12）は未実装。`scoringStatus` は `provisional` 固定

## 5. 検証方法

```bash
npm run lint
npm run typecheck
npm test      # 41件
npm run build
npm run dev   # http://localhost:3000
```

実画面で最低限これを確認すること。ビルド成功を画面確認の代わりにしないこと。

1. 11種類すべての打席結果を選択・記録できる
2. 単打→単打→本塁打で3得点、走者クリア
3. 三振3つで表裏が切り替わり走者が消える
4. 走者一塁で犠打 → 走者が二塁へ（今回の修正点）
5. 2アウト三塁で犠打 → 得点0のまま3アウト（規則5.08(a)）
6. 取消で走者・アウト・打順まで正しく戻る
7. 375px でページ全体が横にはみ出さない
8. 打者一巡で同じ回に2打席立つと、紙スコアのマスに縦に2つ並ぶ

### 検証環境の制約

**ブラウザのビューポート擬似変更では `resize` も `ResizeObserver` も発火しない**（`innerWidth` は変わるのにイベント0件であることを実測で確認）。そのため `PaperScorePreview` の横スクロール案内は、読み込み時の判定（375/768/1024/1440pxで確認済み）しか検証できていない。表示中に画面幅が変わる経路は未検証。実機の回転で確認できる。

`env(safe-area-inset-bottom)` による画面下固定バーのホームバー回避も、擬似環境では inset が0になるため実機未検証。
